## [0.2.0] - 2026-11-25

Updates from within the panel (E-185, E-187, E-188). From this version on, the panel updates itself and the scripts of its servers from signed releases; installations of 0.1.0 move to 0.2.0 once by hand with `get-owpanel`.

### Added
- The panel keeps the scripts of its servers on its own version (E-188): after every status check a server with other scripts gets `server-scripts-update`, at most every 15 minutes, also after being offline. Until then only backups, maintenance and reading tasks start there; other tasks fail with a clear message. The archive comes from the release folder; `panel-update --fetch-archive` loads it for installations with `get-owpanel`, and the installer of a test build writes an unsigned one. New alert "Server scripts outdated" after 30 minutes, with all-clear.
- Server script `server-scripts-update` (E-187): installs the server scripts of a release that the panel sends over stdin, signature first, checked against `/etc/owpanel/release-signers` before anything is unpacked; only `server/` and `VERSION` are used, installed by the new `setup-agent --keep-key`. Never an older release. Test builds (`unsigned`) only on servers whose installer was a test build itself (`/etc/owpanel/allow-unsigned`). The panel uses it in a following step.
- Server script `panel-update` (E-185), the first step of updating the panel from within: `panel-update --version x.y.z` downloads a tagged release of the project from GitHub, checks its checksum and its signature against `/etc/owpanel/release-signers`, and runs the installer of the new release in the background (unit `owpanel-update`), after waiting up to ten minutes for running tasks. Only newer versions are taken. `panel-update --status` reports the state of the last update.
- Update the panel from within (E-185): under **Server → Updates** the card OWPanel links to the release notes of a newer version and installs it after confirming; the page follows the update and reloads when the new version runs. Optionally the panel installs patch versions by itself at night (at 4:47, a day after the release at the earliest, postponed while tasks run). New notifications "OWPanel updated" and "OWPanel update failed".
- The documentation explains uploads from the command line: `scp`, `lftp mirror -R` and `rclone` over SFTP, and why `rsync` does not work for website users.
- Own nginx rules per website (E-184): under Website -> Web server administrators add extra response headers ("Name: value", e.g. HSTS or a Content-Security-Policy) and blocked paths (a folder ending in /, or exactly one file; answered with 404). The new script `site-nginx` checks every line against strict patterns, writes it in a fixed form, tests nginx and keeps the previous rules if nginx refuses. There is no free nginx text. A rebuild from a backup writes the rules again.

### Changed
- Server → State lists the services one below the other, with the PHP-FPM versions in a second column.
- The documentation starts with a choice between "Documentation for administrators" (`/docs/admin/`) and "Documentation for customers" (`/docs/customer/`); the sidebar shows only the pages of one of them, under a plain heading. The panel's "Documentation" link for administrators leads to `/docs/admin/` (E-183).
- The website shows version 0.1 instead of "early development" and links to the source code.
- The start page, introduction and READMEs describe OWPanel as native instead of "without Docker", since Docker apps for administrators are planned.
- The website adds a hash of the content to the addresses of its CSS and JavaScript, so browsers fetch a changed file at once instead of keeping the old one for up to 7 days.

### Fixed
- Server → Updates: "Last update" shows "–" instead of nothing before the first update of the panel.
- Security: `web-auth/webauthn-lib` (passkeys) updated from 5.3.12 to 5.3.14; `composer audit` reported six advisories for versions below 5.3.13, among them metadata and attestation trust path checks.
- "Correct all" on the DNS page no longer ends in "504 Gateway Time-out": the panel waited up to 30 seconds per record (twice when the TTL changed) for Hetzner. A request now waits at most 40 seconds in total; changes Hetzner is still applying then count as done, and the message says to check again in a minute.

## [0.1.0] - 2026-11-23

First public release. It runs as a single server (standalone); the history before this release is not public (E-181).

### Added
- The installation guides show the SHA-256 checksum of `get-owpanel`, and a test keeps it in line with the script (E-071, E-180).
- Documentation for customers (E-178): the website documentation has the groups "For administrators" and "For customers"; seven new customer pages (getting started, website, PHP, databases, cron jobs and logs, backups, moving a website). Customers see "Help" in the panel footer, leading to these pages in their language or to an own help page set under System -> Settings.
- Documentation: websites send mail over SMTP with their own credentials; OWPanel does not relay mail and `mail()` fails (E-177).
- Compression, browser cache and session cookies (E-176): NGINX compresses text responses of the panel and all websites with gzip; websites let browsers keep CSS and JavaScript for 7 days and images, fonts, media and PDF for 30 days. PHP sessions of websites use `HttpOnly`, strict mode and `SameSite=Lax` cookies, `Secure` while a certificate covers the website; applications can still change these values.
- Faster pages (E-175): the installer writes Laravel's caches (`artisan optimize`); the firewall bans and blocklists, server and website logs and the SSH page load what they read from the server after the page has shown; the index of a blocklist stays in the file cache until the list changes; the SFTP page asks sshd at most every ten minutes.
- PHP settings per website (E-173): memory per request, largest upload, longest run time and showing errors, for administrators and the customer of the website, within the package. Packages get limits for these and the PHP processes per website (new packages: 512 MB, 128 MB, 300 s, 10 processes); a change applies at once. The values are php_admin_value and cannot be raised by `.user.ini`.
- fail2ban jail `owpanel-hidden` (E-174): NGINX writes refused requests for hidden files such as `.env` or `.git` of all websites and the panel to `/var/log/nginx/owpanel-hidden.log`; an address with 5 of them within 10 minutes is banned from the web ports for 24 hours. The firewall page names the jails.
- PHP version per website (E-172): PHP 8.5 (default) or 8.6, chosen when creating a website and switched by administrators and the customer of the website. Older versions are not offered. Further versions are installed only as final releases from sury.org; `php` stays on 8.5 for the panel and tools, cron jobs use the website's version. `server-status` reports the installed versions, shown under Server → State.
- Placeholder page for websites (E-171): while `htdocs/public` has neither `index.php` nor `index.html`, nginx shows a bilingual page with the domain for the start page instead of 403, also after the customer deleted everything. The page lives under `/var/lib/owpanel/welcome/`; an own one can be placed as `/etc/owpanel/site-welcome.html` (`@DOMAIN@` is replaced). The installer now writes the configuration of all websites again on every run except first installations and restores (`owpanel:refresh-sites`, `site-create --existing`), so new templates reach existing websites.
- Blocklists in the firewall (E-170): under Server -> Firewall up to ten HTTPS blocklists per server, each with an optional name, checked for their format when added and fetched again every hour, every 6 hours or once a day (`owpanel:blocklists`). `server-blocklist` loads them into an own table `inet owpanel_block` that only drops, after the fail2ban exceptions and the panel's addresses. A list that fails twice in a row raises the notification "Blocklist cannot be fetched" (group Security), with an all-clear on the next success. Refused addresses are counted on the server (`hits4`/`hits6`, kept across list updates, seven days without a hit and they drop out); the firewall page shows the 20 most frequent with their lists and the hits per list. The card warns when own addresses (servers, the current address, "Never ban") are on a list, and "Check address" looks up any single address.
- Signed releases (E-167): a separate GitHub Actions job without build code signs every archive with `ssh-keygen -Y sign` (secret `OWPANEL_RELEASE_SIGNING_KEY`, public key in `release-signers`). `get-owpanel` checks the signature: releases without a valid one are refused, unsigned test builds install with a warning. The installer keeps the key in `/etc/owpanel/release-signers` for later updates of the server scripts.
- Version of the server scripts (E-167): `setup-agent` writes the archive version to `/opt/owpanel/VERSION`, `server-status` reports it as `scripts_version`, and Server -> State shows it with a hint when it differs from the panel. `server-status` also reports the fingerprints of the keys in `/etc/owpanel/release-signers` as `release_keys`; Server -> State shows them with a green check when they match the `release-signers` of the panel's own release, and a red warning when not.
- Server -> SSH (E-155): shows whether administrators may log in over SSH with a password and which login accounts have a key, and turns password login off (refused while an account has no key) or on again with the new script `server-ssh`; SFTP customers keep their password. The SFTP page warns administrators when `AllowUsers`/`AllowGroups` keep `owpanel-sftp` out.
- Updates by hand (E-154): "Check now" refreshes the package lists first, "Install all" installs the listed updates with the new script `server-upgrade` (dist-upgrade, keeping changed configuration files). The update page of the panel server shows the installed and the newest published panel version, with a disabled "Update panel" button until milestone 8.
- Server -> DNS (E-153): A and AAAA of the server's host name, checked and set in a Hetzner zone like for websites, and reverse DNS (PTR) of its IPv4 and IPv6 address, shown with a check that the name points back and, for Hetzner servers, set or reset through the Hetzner Cloud API.
- One way to follow server tasks (E-152): pages stay where they are, the button that started a task shows a spinner with what is happening, and the page reloads when the task is done, with a green or red message (failed tasks link administrators to the log). No more jump to the task page; status badges only appear after a failure.
- Suspend websites (E-127, E-151): new page "Suspension" of a website with an internal note and the option to lock the customer's access. The new scripts `site-suspend` and `site-unsuspend` show a neutral page with HTTP 503 (Let's Encrypt path stays open), rest PHP-FPM and cron and lock SFTP, and bring back exactly the previous state. While suspended, customers can only look and administrators can only unsuspend, delete, back up, restore and export; pages show a banner and disabled forms. A rebuild from a backup suspends the website again.
- Test builds and website builds are kept 7 instead of 30 days; 30 days had filled the artifact storage, so new builds failed. `get-owpanel --dev` now warns when the newest build of the branch failed or is still running, instead of silently installing an older one.
- A locked customer access now shows a red message above the sign-in form instead of a hint under the address field, which looked like wrong credentials (E-151).
- The installer asks for the host name on a first installation (E-150): it shows the current name, keeps it or sets a new one in `/etc/hostname` and `/etc/hosts` with a rollback on failure, tells cloud-init to keep it, and reminds of the reverse DNS; unattended runs use `--hostname`.
- Storage per customer (E-126, E-149): the base setup turns on Linux user quotas for `/var/www` on ext4 (`/etc/fstab` checked with `findmnt --verify`, rollback on failure); the new scripts `site-usage` and `site-quota` measure files and databases every 15 minutes and give each website the hard limit "own files + free space of the customer". ### Fixed
- Websites accepted uploads of at most 1 MB, the default of nginx; `client_max_body_size` now follows the upload setting of the website (E-173).
- PHP-FPM 8.6 did not start: the idle www pool of every version listened on the same socket. Each version now has its own (`owpanel-idle-<version>.sock`), and the pool is written before PHP-FPM starts.
- A further PHP version whose PHP-FPM does not start (seen with PHP 8.6) stopped the base setup. It now gives a warning, is switched off and is not offered; `server-status` lists only running versions (E-172).
- The base setup failed on a fresh Debian with `unexpected_error` in the quota module: `/var/www` did not exist yet, and `findmnt --target` fails for a missing path. The module now creates it first and falls back to measuring only if the file system stays unknown.
- The installer's DNS check for the panel domain asks DNS only. With the host name as panel domain, `/etc/hosts` answered 127.0.1.1 and the check failed although DNS pointed to the server.
- The message "backup finished" names only the backups started together in one run: a website created after the night's run gets its own message with its own duration, and the panel's first backup after connecting the Storage Box no longer appears twice
- After the first restart following the installation, all times stored before showed one hour too late (e.g. tasks "in the future") and the restart hint stayed up to two hours: MariaDB converted TIMESTAMP columns with the server's new time zone. The panel now uses UTC for its database session
- After restoring the panel, System -> Backup did not say which backup it came from: the settings were read from the cache in the restored database; the installer now clears it. The panel server's backups now connect again by themselves at the end of the restore instead of by "Save and connect"
- Server -> Backups: the status of the last backup sits below its time, so the table no longer runs off the card
- On a fresh server the installer failed or stood still while apt-daily and unattended-upgrades installed the first updates. A first installation, a restore included, now pauses the automatic updates, installs all pending updates itself before the base services and again at the end, has the panel check the update state anew and offers the restart; the automatic updates resume after that restart. Other scripts pause them only while they install packages; installs are tried up to three times (E-102)
- Restoring the panel in the installer failed with "unable to start the sftp session": SSH could not ask for the subaccount password inside restic. The installer now asks for it itself, hands it to SSH with sshpass, tests the login first with a clear message, and accepts the home directory from the emergency data as repository
- Moving the backup or snapshot time later on the same day now runs it again at the new time; a run counted for the whole calendar day before

- "Package lists updated" also shows a date when apt does not write update-success-stamp; the newest Release file counts as well.
- The reboot hint disappears within a minute after a restart instead of waiting for the hourly update check (E-080).
- Copy buttons also work when the panel is reached over plain HTTP (no Clipboard API outside a secure context).
- The task page shows the website label in its details (missing translation key).
